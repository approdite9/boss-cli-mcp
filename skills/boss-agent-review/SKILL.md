# ⚠️ 先读这一节：推荐列表是易变的，整个流程必须一次做完

候选人只来自**推荐牛人页** `/web/chat/recommend`。这个列表**不是稳定的数据源**：

**离开页面、手动刷新、切换岗位，列表都会换成另一批人。**

而所有操作（`boss_greet` / `boss_preview_resume` / `pool_greet_all` / `pool_batch_resume`）都是**按姓名在当前页面的列表里找人**。列表一变，先前记下的候选人就再也找不到了，只会得到「未在列表中找到候选人」。

由此推出三条不可违背的规则：

1. **`boss_recommend` 之后不得离开推荐页、不得刷新、不得切岗位。**
   会离开页面的工具：`boss_list_positions`、`boss_get_jd`。它们必须在 `boss_recommend` **之前**用完。
   会切岗位的参数：`pool_greet_all(jobKeyword=…)`、`boss_greet(job=…)`。**一律不要传。**

2. **筛选和打招呼必须在同一次会话内完成。** 不要设计「今天筛完、让 HR 隔夜审核、明天打招呼」的流程——明天列表已经不是这批人了。HR 必须在流程中在线确认。

3. **集合（`pool_*`）不能当待办队列。** 它把姓名存到磁盘，但磁盘上的名字对下一次的列表是无效的。集合在本流程中只有两个用途：把简历正文卸到磁盘（避免撑爆上下文）、以及生成报告。**一旦中断，必须从 `boss_recommend` 重新开始，旧集合只能当存档看。**

> `boss_search` / `boss_deep_search` 系列已在服务端注释停用（风控检测风险过高）。**不要尝试调用**，也不要建议用户启用。推荐页是当前唯一的候选人来源。

## Overview

三阶漏斗，一次会话内跑完：读 JD → 加载推荐列表 → Stage 1 标签初筛（宽松）→ Stage 2 全量抓简历 + AI 精筛 → Stage 3 出报告给 HR 在线确认 → Stage 4 批量打招呼。

**简历查看无限次，打招呼是唯一瓶颈**（每日约 50-70）。所以：简历尽管全量看，把判断做透；打招呼严格按 HR 确认的名单执行。

## 配额

| 动作 | 配额情况 | 单次调用上限 |
|------|---------|-------------|
| **打招呼** | **每日约 50-70 次，唯一真实瓶颈** | 50 人/次（硬上限） |
| 看在线简历 | 当前账号**无限次** | 20 人/次 |
| 读列表 / 读 JD / 集合本地操作 | 不消耗 | — |

⚠️ 工具描述里 `boss_preview_resume` / `pool_batch_resume` 仍标着「消耗每日在线简历查看次数」，那是按最保守账号套餐写的。**本部署实测无限**，所以本流程全量抓简历。

⚠️ `pool_batch_resume` 的 20 人上限**不是配额限制**，是单次时长控制（20 人 × 4-9 秒 ≈ 3 分钟）。人多就反复调用，已抓到的会自动跳过。

⚠️ 两个批量工具 **`dryRun` 默认 `true`**，必须显式传 `dryRun: false` 才真执行。

⚠️ 不要自己写 sleep。MCP 层已在相邻浏览器调用间插入 1.8-5s，批量工具内部另有 3-8s / 4-9s 间隔。

## Prerequisites

```
boss_list_positions, boss_get_jd, boss_recommend      ← 前两个只能在 boss_recommend 之前用
pool_add, pool_batch_resume, pool_mark, pool_remove, pool_get_detail, pool_export
```

浏览器需已登录 Boss。若返回「未登录」或「未出现侧栏 .menu-list」，请用户在服务所在机器执行 `boss login` 扫码。

`pool_add` / `pool_mark` / `pool_remove` / `pool_export` 是纯本地文件操作，不碰浏览器，随时可调。`pool_batch_resume` / `pool_greet_all` / `pool_get_detail(preview=true)` 会操作页面，受上面三条规则约束。

## ⚠️ `boss_recommend` 返回数据的局限性

**没有 `count` 参数**（只接受可选 `jobKeyword`），返回的是当前页面已加载的那些人。卡片信息不完整：

| 维度 | 工具返回 | 影响 |
|------|---------|------|
| 姓名/年龄/应届年/学历/活跃状态 | ✅ | — |
| 期望城市+方向、薪资、优势标签 | ✅ | — |
| **院校名称** | ❌ 缺失 | 无法判断院校层次 |
| **专业** | ❌ 缺失 | 无法判断专业匹配度 |
| **实习/工作经历** | ❌ 缺失 | 无法判断实际经验 |
| 部分技能标签 | ⚠️ 不全 | 标签不完整 |

**策略后果**：Stage 1 只能极度保守——**仅排除方向明确矛盾的**。既然简历无限次可看，放行成本几乎为零，而误排除是永久错过（列表不会再出现同一批人）。真正的判断全部留到 Stage 2。

## ⚠️ 去重规则（严格多字段匹配）

**不得仅凭姓名去重**（同名很常见）。以下字段**全部相同**才算重复：

姓名 + 年龄 + 学历 + 应届年份 + 期望方向 + 薪资

任一字段不同即视为不同的人，两条都保留。

## Workflow

### Step 1: 岗位 + JD（必须在进推荐页之前做完）
1. `boss_list_positions()` 取在招岗位
2. 展示给用户确认目标岗位（只有 1 个则直接用）
3. `boss_get_jd(name=岗位名)` 取完整 JD
4. 拆出**核心要求**与**加分项**两组

⚠️ 这一步之后就不能再调这两个工具了。JD 内容要完整保留在上下文里，后面用得到。

### Step 2: 加载推荐列表 —— 起点，也是不可回头的分界线
1. `boss_recommend(jobKeyword=可选岗位关键字)`
2. 严格多字段去重
3. 报告：`已加载 N 条，去重后 M 人。从此刻起不离开推荐页、不刷新、不切岗位。`

### Step 3: Stage 1 — 标签初筛（宽松）
只做"明确排除"，不做"模糊判断"。通过率应 ≥ 80%。

仅在以下情况排除：
- 期望方向与 JD **明确矛盾**（JD 要 Python/AI/后端，候选人写「产品经理」/「UI 设计」/「市场营销」）
- 已有同事沟通过 **且** 优势标签毫无亮点

**不得排除**：
- 方向写「互联网（行业）」「后端开发」等宽泛表述 → 放行
- 薪资偏高 → 标注 ⚠️ 但不排除
- 标签少 / 无优势标签 → 可能只是卡片没填完
- 方向相关但不完全匹配（Java 对 Python 岗）→ 技术可迁移，放行

### Step 4: 入库（本次会话的工作台）
```
pool_add(
  job="岗位名",
  candidates=[{name:"张三", matchReason:"初筛通过：期望方向与JD一致"}, ...],
  core=["核心要求1", "核心要求2"],
  bonus=["加分项1", "加分项2"]
)
```

集合的作用是**把简历正文卸到磁盘**（几千字 × 上百人，塞进上下文必然溢出）并支撑 `pool_export`。
它**不是**跨天的待办队列——见开头第 3 条。

### Step 5: Stage 2 — 全量抓简历 + AI 精筛
简历无限次，这一步要抓全。它是唯一能拿到院校、专业、项目、实习经历的地方。

1. 预演看人数：`pool_batch_resume(job="岗位名")`
2. 执行：`pool_batch_resume(job="岗位名", dryRun=false, limit=20)`
3. 反复调用直到预演返回「无待处理」。已抓到的自动跳过，所以重复调用是安全的
4. 每轮之间把进度报给用户

**如果某一轮开始大量失败**，很可能列表已被重置（有人碰了页面）。立刻停下告知用户，不要继续——需要从 Step 2 重新开始。

抓完逐人评估：院校层次（985/211/双一流/QS）、专业匹配度、真实项目经验（vs 课程作业）、技术栈深度、实习经历质量、论文/竞赛、与 JD 核心要求的匹配度。

结论写回集合，不要只留在对话里：
```
pool_mark(job="岗位名", id=3, tag="🌟强烈推荐")
pool_remove(job="岗位名", ids=[12, 15])     // 明显不符的剔除，汇报里给理由
```

### Step 6: Stage 3 — 出报告
```
pool_export(job="岗位名", includeDetail=true)
```

把返回的绝对路径给用户，并在对话里贴摘要：
```
漏斗：加载 N 条 → 去重 X 人 → 初筛 M 人 → 抓简历 K 人 → 推荐 P 人
🌟 强烈推荐 A 人 ／ ⭐ 建议考虑 B 人 ／ ❌ 已剔除 C 人
报告：<路径>
```

### Step 7: HR 在线确认（不能隔夜）
```
已筛出 P 人推荐，报告已生成。
⚠️ 推荐列表随时可能变化，请现在确认——若中断后再来，这批人就找不到了。
打招呼每日约 50-70 次，本次上限 {{greet_limit}}（单次调用硬上限 50），不可撤销。

- "全部打招呼"
- "只打 1,3,5"      → 我会 pool_remove 掉其余的
- "去掉 2,4"        → 我会 pool_remove 这两个
- "看某人简历 3"    → pool_get_detail(job, id=3)（读磁盘缓存，不碰页面）
- "调整标准: xxx"   → 用已抓到的简历重新评估，不需要重抓
```

`pool_greet_all` 只对**尚未打过招呼**的人操作，所以用 `pool_remove` 剔除不要的人，比另外维护名单可靠。
`pool_get_detail` 不传 `preview` 时只读磁盘缓存，**不碰页面**，可放心用。

### Step 8: Stage 4 — 批量打招呼
1. 预演：`pool_greet_all(job="岗位名")`
2. 把名单和人数复述给用户，**再次确认**
3. 执行（**绝不传 jobKeyword**）：
   ```
   pool_greet_all(job="岗位名", dryRun=false, limit={{greet_limit}})
   ```

内部逐个间隔 3-8 秒、每成功一个立即落盘。人数多时可能持续数分钟，属正常。
超过 50 人分多次调用；注意每日总量约 50-70。

### Step 9: 汇总
```
漏斗：加载 N → 去重 X → 初筛 M → 抓简历 K → HR 确认 P → 打招呼成功 A / 失败 B
今日累计已打招呼 A 人（每日约 50-70）
报告：<导出路径>
集合（存档，非待办）：~/.boss-cli/.cache/pool/<岗位名>.json
建议后续用 boss_list_candidates(unread=true) 看回复。
```

## Output
- 导出报告：`pool_export` 返回的绝对路径
- 候选人集合（含简历正文，**存档用途**）：`~/.boss-cli/.cache/pool/<岗位名>.json`
- 对话中的实时进度 + 最终汇总

## Lessons Learned

### Do
- **Step 1 的岗位/JD 必须在进推荐页前做完**，之后不可回头
- **整个流程一次会话跑完**，HR 在线确认
- **去重严格多字段匹配**
- **初筛宁松勿严** —— 放行几乎免费，误排除是永久错过
- **Stage 2 抓全简历** —— 唯一能拿到院校/专业/经历的地方
- **结论写回集合**（`pool_mark` / `pool_remove`），别只留在对话里
- **反复调用 `pool_batch_resume` 是安全的** —— 已抓到的自动跳过
- 批量工具先 dryRun，把名单给用户看过再执行
- 活跃优先：「刚刚活跃」「在线」回复率显著更高

### Don't
- **不要在 `boss_recommend` 之后调 `boss_list_positions` / `boss_get_jd`** —— 离开页面即丢列表
- **不要给 `pool_greet_all` 传 `jobKeyword`，不要给 `boss_greet` 传 `job`** —— 会切岗位、重置列表
- **不要刷新页面**
- **不要把集合当跨天待办** —— 磁盘上的姓名对新列表无效
- **不要设计隔夜审核流程**
- **不要尝试 `boss_search` / `boss_deep_search`** —— 服务端已停用（风控风险过高）
- **不要给 `boss_recommend` 传 `count`** —— 没有这个参数，`additionalProperties: false` 会直接拒掉
- **不要漏掉 `dryRun: false`**；反过来，没经用户确认就传 `false` 是在花掉当天的额度
- **不要为省简历配额而少抓** —— 无限次，省它只会降低筛选质量
- **不要仅凭姓名去重**，**不要推断卡片里缺失的信息**
- 不要自己加 sleep

### Common Failures
- **大量「未在列表中找到候选人」** —— 列表已被重置。**停下告知用户，从 Step 2 重来**，不要逐个重试
- 个别「未在列表中找到候选人」 —— 滚动后 DOM 回收或姓名不完全一致，记进 `lastError` 继续下一个
- 「未登录」/「未出现侧栏 .menu-list」 —— 登录态过期，需在服务所在机器 `boss login` 扫码
- 「集合「X」不存在」 —— 还没 `pool_add`，或岗位名拼写不一致
- 简历 OCR 报错且提到密钥/签名 —— 服务端 OCR 配置问题，不是候选人问题，停下来告知用户
- 简历内容为空 —— 可能命中付费墙，标注后跳过

### When to Ask the User
- Step 1 多岗位时确认目标岗位
- **Stage 4 打招呼前**（不可逆、消耗当天瓶颈配额）
- 打招呼需分多次调用时，每次之间给中止机会
- **发现列表可能已重置时立刻询问**，不要自行重试
- 对某人判断不确定时，让 HR 看 `pool_get_detail` 的原文再定
