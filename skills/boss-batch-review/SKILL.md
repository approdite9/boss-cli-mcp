## Overview

在推荐页分批展示候选人，由 HR 实时决定对每个人打招呼或跳过。每批展示前**先批量预览简历**补齐院校/专业/经历，确保 HR 基于完整信息决策。

**与 `boss-agent-review` 的分工**：本流程把判断权交给 HR，Agent 只负责组织信息和执行操作；`boss-agent-review` 则由 Agent 先做两轮筛选、HR 只确认最终名单。人少或标准难以言明时用本流程，人多且信任 Agent 判断时用后者。

本流程**刻意不使用 `pool_*` 集合工具**：HR 全程在场、每批当场决策、状态活不过当前批次。为了「打招呼 1,3」两个人去建集合再剔除其余八个，只增加出错面而没有收益。需要留档时在最后一次性 `pool_add` 即可。

## 配额

| 动作 | 配额情况 |
|------|---------|
| **打招呼**（`boss_greet`） | **每日约 50-70 次，这是唯一的真实瓶颈** |
| 看在线简历（`boss_preview_resume`） | 当前账号**无限次**，可放心全量查看 |
| 读列表 / 读 JD | 不消耗 |

⚠️ 工具描述里 `boss_preview_resume` 仍标着「消耗每日在线简历查看次数」，那是按最保守的账号套餐写的。**本部署实测无限**，所以本流程全量预览简历。若换账号后发现开始受限，再改回按需查看。

⚠️ 不要自己写 sleep。MCP 层已在相邻浏览器调用之间插入 1.8-5s 随机间隔。

## Prerequisites

需要以下 MCP 工具（工具名前缀随客户端而异，本文按裸名书写）：

```
boss_list_positions, boss_get_jd, boss_recommend
boss_preview_resume, boss_greet
pool_add            （可选，仅用于最后留档）
```

浏览器需已登录 Boss。若返回「未登录」或「未出现侧栏 .menu-list」，请用户在服务所在机器执行 `boss login` 扫码。

## ⚠️ 最重要的约束：进入推荐页后不得离开、不得切岗位

`boss_preview_resume` / `boss_greet` **要求当前已在「推荐」`/web/chat/recommend` 页且列表已加载，它们不会自动跳转**，并且**必须能在当前列表里按姓名找到该候选人**。

一旦列表被重置，之前 `boss_recommend` 拿到的候选人就再也找不到了。会导致重置的动作：

- `boss_list_positions` / `boss_get_jd` —— **会离开推荐页**
- 切换岗位 —— 会重置列表
- 大幅滚动 —— DOM 回收，靠后的卡片可能失效

所以顺序是死的，且中途不可回头：

```
boss_list_positions → boss_get_jd → boss_recommend → 之后只做 preview / greet
```

> 备注：`boss_search` / `boss_deep_search` 系列工具已在服务端注释停用（风控检测风险过高），不要尝试调用。

## ⚠️ `boss_recommend` 返回数据的局限性

**没有 `count` 参数**（只接受可选 `jobKeyword`），返回的是当前页面已加载的那些人。卡片信息不完整：

| 维度 | 工具返回 |
|------|---------|
| 姓名/年龄/应届年/学历/活跃状态 | ✅ |
| 期望城市+方向、薪资、优势标签 | ✅ |
| **院校名称** | ❌ 缺失 |
| **专业** | ❌ 缺失 |
| **实习/工作经历** | ❌ 缺失 |
| 部分技能标签 | ⚠️ 不全 |

**因为简历无限次可看，这个缺口用 `boss_preview_resume` 补齐**——每批展示前先把该批次的人的简历抓下来，再以完整信息呈现给 HR。不要只拿卡片标签就让 HR 决策。

## ⚠️ 去重规则（严格多字段匹配）

**不得仅凭姓名去重**（同名很常见）。以下字段**全部相同**才算重复：

姓名 + 年龄 + 学历 + 应届年份 + 期望方向 + 薪资

任一字段不同即视为不同的人，两条都保留。

## Workflow

### Step 1: 岗位 + JD + 参数
- **Mode**: `agentic`
- **Validate**: 至少 1 个岗位

1. `boss_list_positions()` 取在招岗位
2. 展示并让用户确认目标岗位（只有 1 个则直接用）
3. `boss_get_jd(name=岗位名)` 取完整 JD
4. 拆出核心要求 / 加分项摘要，后续展示时作参考
5. 确认 `batch_size`（默认 {{batch_size}}）

### Step 2: 加载推荐列表
- **Mode**: `deterministic`
- **Validate**: 去重后 > 0 人

1. `boss_recommend(jobKeyword=可选岗位关键字)`
2. 严格多字段去重
3. 按活跃度排序（「刚刚活跃」「在线」优先，回复率显著更高）
4. 报告：`已加载 N 条，去重后 M 人，分 X 批展示（每批 {{batch_size}} 人）`

⚠️ **从此刻起：不离开推荐页、不切岗位。** 这是本流程唯一不可恢复的错误。

初始化计数：`已打招呼 0`

### Step 3: 批量预览简历 + 展示一批
- **Mode**: `agentic`
- **Validate**: 用户回复了有效指令

1. 对当前批次每人调 `boss_preview_resume(name=姓名)`（无限次，放心抓）
2. 从简历提取：院校、专业、实习/工作经历（公司+方向）、项目亮点
3. 以完整信息展示：

```
【第 X 批 / 共 Y 批】已打招呼 B 人（每日约 50-70）
JD 核心要求：[摘要]

| # | 姓名 | 院校·专业 | 学历 | 应届 | 方向 | 薪资 | 活跃 | 实习/经历 | 推荐度 |
|---|------|----------|------|------|------|------|------|----------|--------|
| 1 | 向锐 | 电子科大·计算机 | 硕士 | 2026 | Python | 15-30K | 在线 | 字节·模型评测 | 🌟 |
| 2 | 龚昱帆 | 四川大学·计算机 | 本科 | 2027 | 互联网 | 面议 | 在线 | 算秩未来·Golang | ⭐ |

请回复：
- "打招呼 1,3"  → 对指定编号打招呼（消耗每日打招呼次数）
- "全部打招呼"
- "看原文 2"    → 展示该候选人简历全文
- "下一批"
- "结束"
```

推荐度：🌟 方向匹配且有实质经历/项目 ／ ⭐ 部分匹配或有潜力 ／ ➖ 匹配度较低（仍展示，由 HR 决定）

一次不超过 15 人，表格太长影响可读性。若某人简历抓取失败或为空，在表里标「简历不可用」，不要因此跳过展示。

### Step 4: 执行指令
- **Mode**: `agentic`
- **On failure**: 记录原因，继续下一个

| 指令 | 动作 |
|------|------|
| `打招呼 1,3` | 逐个 `boss_greet(name=…)`。**执行前复述姓名让 HR 确认**——不可撤销 |
| `全部打招呼` | 对当前批次所有人 |
| `看原文 2` | 展示已抓到的简历全文 |
| `下一批` | 回 Step 3 |
| `结束` | 进 Step 5 |

⚠️ **调用 `boss_greet` 时不要传 `job` 参数。** 岗位在 Step 2 已经确定，再传会触发岗位切换、重置列表，后面的候选人全部找不到。

每次操作后展示计数：`✅ 完成。已打招呼 X 人（每日约 50-70）。`

累计接近 50 时提醒 HR 配额即将耗尽。

### Step 5: 汇总

```
本次审核完成：
浏览 N 人（M 批）／打招呼 X 人（成功 A / 失败 B）／查看简历 Y 份
今日累计已打招呼 X 人（每日约 50-70）
```

需要留档，此时（流程已结束，不再依赖列表）可一次性入库：

```
pool_add(job="岗位名", candidates=[{name:"…", matchReason:"已打招呼 / HR 认可"}…])
```

之后 `pool_export(job="岗位名")` 可出一份 Markdown 存档。

## Output

- 对话中的分批完整信息表格 + 实时操作反馈 + 汇总
- 可选：候选人集合 `~/.boss-cli/.cache/pool/<岗位名>.json` 与导出报告

## Lessons Learned

### Do
- **Step 1 先取岗位+JD**，进入推荐页后就不能再离开
- **每批展示前先全量抓简历** —— 简历无限次，卡片缺院校/专业/经历，不补齐就是让 HR 盲选
- **去重严格多字段匹配**
- 活跃优先排序
- 每批只展示当前批次，不重复前几批（省上下文）
- 操作后立即展示打招呼计数，让 HR 实时知道瓶颈消耗
- 简历抓取失败的人照样展示，标注「简历不可用」

### Don't
- **不要给 `boss_recommend` 传 `count`** —— 没有这个参数，`additionalProperties: false` 会直接拒掉
- **不要给 `boss_greet` 传 `job`** —— 会切岗位、重置列表，后续候选人全丢
- **不要在流程中途调 `boss_list_positions` / `boss_get_jd`** —— 会离开推荐页
- **不要尝试 `boss_search` / `boss_deep_search`** —— 服务端已停用（风控风险过高）
- **不要仅凭姓名去重**
- **不要在 HR 确认前打招呼**
- 不要自己加 sleep
- 不要一次展示超过 15 人
- 不必为本流程建 pool 集合 —— HR 在场、状态短命，留档放到最后即可

### Common Failures
- 「未在列表中找到候选人：X」 —— 不在当前推荐列表（滚动后 DOM 回收，或姓名不完全一致）。记录失败继续下一个，**不要试图重新加载列表**
- 「未登录」/「未出现侧栏 .menu-list」 —— 登录态过期，需在服务所在机器 `boss login` 扫码
- 简历 OCR 报错且提到 OCR 密钥/签名 —— 服务端 OCR 配置问题，不是候选人问题，停下来告知用户
- 简历内容为空 —— 可能命中付费墙，标「简历不可用」
- 推荐页 0 人 —— 检查岗位是否开放中

### When to Ask the User
- Step 1 多岗位时确认目标岗位
- **每次打招呼前**（不可逆、消耗每日瓶颈配额）
- 打招呼累计接近 50 时提醒
- 用户要求离开推荐页时**必须警告**：会丢失全部候选人且无法恢复
